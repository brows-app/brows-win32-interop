## Summary

The branch moves Brows.Operations from 1.5.0 to 1.6.0. It makes `Win32FileOperation.Operate` throw an
`OperationCanceledException` that carries the caller's token when the progress sink stops the Shell. Without
that change, a batch canceled mid-run returned `true`, which 1.6.0 would report as `Succeeded`. It also
documents the new cancellation contract, adds regression tests, adds `InternalsVisibleTo` for the
Operations test assembly, and suppresses CS8981 on `ntdll` and `winerror`.

The code change is sound and covered by tests. One documentation inaccuracy was confirmed.

## Findings

### #1 [P3] README says a canceled batch returns a Canceled result under Record, but parent cancellation throws [Resolved]

- Status: Resolved
- Location: `source/Brows.Win32.Interop.Operations/README.md:76-77` (target revision)
- Problem and trigger: The new "Cancellation in operation trees" section shows a batch run inside
  `progress.Child(..., OperationFailureBehavior.Record, default)` and then says: "A canceled batch then
  produces an `OperationResultKind.Canceled` outcome under `Record`." The token passed to `Operate` is the
  child's effective token, which is linked to the parent's token. When the parent operation (or a token
  supplied to `Child`) is canceled, `Child` does not return a result. It throws.
- Impact: A consumer who follows the README may write `if (result.Kind == OperationResultKind.Canceled)`
  and expect that branch to handle every cancellation. When the parent or root operation is canceled, which
  is the usual case for a user canceling the whole tree, `await progress.Child(...)` throws an
  `OperationCanceledException`, so code after the await never runs. Any cleanup placed there is skipped
  unless it is in a `finally` block.
- Evidence: The Brows.Operations 1.6.0 contract for `IOperationProgress.Child`
  (`F:/dev/me/brows-operations`, `source/Brows.Operations/Operations/IOperationProgress.cs:141-143` at
  `3ede110`) says: "Record returns ordinary failure and child-only cancellation outcomes. … Parent or
  supplied-token cancellation and infrastructure failures propagate under either policy." The
  package README says the same ("Parent or supplied-token cancellation and infrastructure errors propagate
  under either policy"). Only child-only cancellation, such as canceling that child operation through
  `Operation.Cancel`, produces a `Canceled` result under `Record`. This is a static trace of the documented
  contract; no runtime reproduction was performed.
- Suggested resolution: Make the sentence specific: under `Record`, canceling only the child operation
  produces `OperationResultKind.Canceled`, while canceling the parent or a supplied token makes `Child`
  throw `OperationCanceledException` under either policy. Optionally add a `try`/`catch` or `finally` to the
  example, or note that cleanup belongs in a `finally` block.
- Verification: Reread the section against `IOperationProgress.Child` remarks. Optionally, in a scratch
  project with Brows.Operations.Composition, cancel the root operation while the child runs and confirm that
  `Child` throws, then cancel only the child and confirm that it returns `Canceled`.

Resolution: Rewrote the paragraph after the example in
`source/Brows.Win32.Interop.Operations/README.md:76-80`. It now says that only child-only cancellation
produces `OperationResultKind.Canceled` under `Record`. When the parent operation or a token supplied to
`Child` is canceled, `Child` throws `OperationCanceledException` under either policy and code after the
`await` does not run, so required cleanup belongs in a `finally` block. The `Throw` guidance is retained.
The example code is unchanged.

Verification: Documentation-only change, so there is no automated red/green test. Reread the revised
paragraph against the Brows.Operations 1.6.0 `IOperationProgress.Child` remarks (`IOperationProgress.cs:141-143`
at `3ede110`) and the package README's "Child outcomes" section; both statements now match the contract.
`git diff --check` reported no whitespace problems. The README's UTF-8 (no BOM) encoding and CRLF line
endings are preserved. A runtime check through a real operator was not run, because this repository does not

## Open questions

- **Cancellation precedence over an earlier Shell failure.** In `Win32FileOperation.cs:166-171`, the new
  `CancellationReported` check runs before `performHr.ThrowOnError()`. If an earlier item failed (for
  example, with access denied under `NoErrorUI`) and the token was then canceled, `Operate` reports
  cancellation and the item failure's HRESULT is not surfaced. Under 1.6.0's `Record` policy, the child
  would be reported as `Canceled` rather than `Failed`. Whether that matters depends on whether
  `PerformOperations` returns a failing HRESULT for per-item failures in that situation. That needs a Shell
  reproduction with a failing item followed by cancellation, and an intended precedence decision.
- **Token carried when the STA pool rejects queued work.** The new `<exception>` documentation says the
  exception "carries `token`" when the batch is stopped before execution. That was verified for the
  already-canceled path (`Task.Run` with a canceled token; covered by
  `Operate_WhenTokenAlreadyCanceled_DoesNotRun`). The `Brows.Win32.STAThreadPool.Contracts` 1.5.1
  documentation does not say which token `ISTAThreadPool.Work` puts on its exception when cancellation
  occurs while work is queued behind other items. To confirm the claim, cancel a batch that is waiting
  behind a blocking work item on a single-worker pool and inspect `OperationCanceledException.CancellationToken`.
  When the caller passes the delegate's own token as documented, 1.6.0 still classifies the exception as
  cancellation, because the operation's token is canceled.
